## Objective

Replace the thin Administrator home with an actionable daily oversight experience covering receptions, production, quality control, raw-material stock, sales, tasks, staff activity and synchronization health. Add a neutral AROM domain for producer invoices linked to raw-material receptions, without exposing or depending directly on Mombongo in the mobile UI.

This sprint prepares invoice review and future payment execution. It must never simulate a payment while no real backend payment adapter exists.

## Confirmed decisions

- MOB-05C quarantine resolution is deferred.
- The AROM UI must never display Mombongo names, logos or technical language.
- Producer invoices cover pineapple now and other raw materials later.
- All Administrator priorities are useful: operational alerts, producer payables, production/stock, sales, staff activity, approvals/tasks and synchronization failures.
- The future external-payment integration and invoice ingestion mechanism are not yet implemented.

## Confirmed MOB-05B baseline

- Quality controls are stored in `qualityControls/{id}` and reference `productionId`.
- One final control is allowed per production lot; concurrent duplicates are rejected transactionally.
- Decisions are `liberer`, `quarantaine` and `rejeter`.
- A control contains the lot/date, sample volume, three aspect checks, conforming/rejected litres, optional reason/comment/photo, and attributable `responsable`/`staffUid` fields.
- `qualityControls` is offline-capable and already participates in the mutation queue and role sync plan.
- A locally queued quality control may depend on an unsynchronized source production.
- A quarantined lot cannot currently be re-controlled or released. MOB-05C remains deferred, so ADMIN may inspect and prioritize it but must not resolve it in MOB-06A.
- There is no finished-goods stock collection. The quality decision's “stock consequence” is explanatory UI copy only and creates no stock write.
- `stockMP` represents raw-material stock only.
- The rules suite has a documented pre-existing first-upload Storage-emulator cold-start race. MOB-06A must not introduce new failures or hide this baseline issue.

## Amendments after research (2026-08-29)

Research required by the section below is complete — see `RESEARCH_NOTES.md`
in this folder for the full citation-backed report. Four points in this
README no longer match reality and are corrected here; everything else in
the spec stands as written.

1. **"Organization isolation" does not apply.** There is no `orgId`/
   `organisationId` field or multi-tenancy concept anywhere in AROM-Backend,
   AROM-Production or AROM-Mobile — access is gated purely by `role`/`poste`.
   Wherever this document or IMPLEMENTATION_PROMPT.md says "organization
   isolation" or "cross-organization access," read it as "role/poste gating
   consistent with the existing `isAdmin()`/`isAdminOrStaff()` rules
   predicates" — the same boundary every other collection already uses.
   Introducing real per-organization tenancy is out of scope for MOB-06A.
2. **`BackHeader` doesn't exist.** It was superseded by a parameterized
   `AppHeader` (`onBack` prop) before this sprint started. Wherever this
   spec says "AppHeader/BackHeader," implement against `AppHeader` only —
   there is nothing to route to.
3. **Task "assignment" is display-only.** `tasks/{id}` has no assignee
   field — every admin/staff account already sees the same pending-task
   list. A6's "task assignment only through the existing task contract"
   means: link into the existing task create/read contract as-is; do not
   add a per-user assignee field or a real assignment mechanic in this
   sprint.
4. **Architecture decision needed up front.** ADMIN currently reuses the
   same generic `RoleHomeScreen` component every other role uses, config-
   driven by `roleHomeConfig.ts`/`roleHomeData.ts`. MOB-06A's six sub-screens
   (A1–A6) are a materially different information architecture from a
   single-screen role home. Decide and record in implementation notes
   whether ADMIN forks into its own screen set (recommended) or the shared
   component grows a large ADMIN-only branch, before building A1.

Two additional pre-existing gaps to build against, not fix:
`AROM-Mobile/src/features/sync/syncPlan.ts` does not yet pull
`qualityControls` or `stockMP` into ADMIN's cache — both must be added to
`getSyncPlan`/`CATEGORY_KEYS_BY_ROLE` before A1/A3 can be honestly
cache-first. `/activity` is currently an explicit empty stub, not a feed to
extend — A2 is new work built from raw collections.

## Recommended architecture decision

Use an AROM-owned normalized `ProducerInvoice` domain. Its UI and business language remain provider-neutral. Future payment execution must go through an AROM backend boundary such as `ProducerPaymentGateway`; mobile must never hold provider secrets or call an external payment provider directly.

If no invoice source exists yet:

- A reception may expose an honest **estimated amount due** only when its real quantity and pricing fields make that calculation valid.
- Do not label an estimate as “invoice received”.
- Do not manufacture invoice documents from reception data.
- Invoice ingestion and actual payment remain capability-gated.

## Entry points

- ADMIN role home becomes the oversight dashboard.
- `Voir les priorités` opens the complete priorities view.
- `Factures producteurs` opens invoice/payables list.
- A linked reception can open its related payable/invoice when one really exists.
- ADMIN quick action may include invoice review only if authorized; do not make payment a generic `+` action.

## Flow A — Administrator oversight

### A1. Vue d’ensemble

- Shared AppHeader, sync status, `Mode Administrateur` badge.
- `À traiter aujourd’hui` ordered by severity and actionable consequence.
- Real operational summaries: receptions, production, quality controls, raw-material stock and sales.
- Do not show “finished products available” or “finished-goods stock” because that domain does not exist.
- Producer payable summary only from real invoice/payable data.
- Primary CTA `Voir les priorités`.
- BottomNav: `Accueil · Tâches · + · Activité · Plus`.

### A2. Activité du jour

- Cross-role chronological events from existing records.
- Filters: Tout, Collecte, Production, Vente, Équipe.
- Actor/role only when verifiable.
- No surveillance score or fabricated productivity measure.

### A3. Suivi des opérations

- Large, photo-led cards for Réceptions, Production, Contrôle qualité, Stock matières premières and Ventes.
- One meaningful real metric and one status per module.
- CTA opens the existing or honest module route.

### A4. Priorités

- Groups: Urgent, À faire aujourd’hui, À surveiller.
- Each item explains why it matters and provides one next action.
- Derived only from supported dates, statuses and rules.
- Quality priorities may include productions with no final control, quarantined/rejected lots requiring ADMIN awareness, and failed quality-control synchronization.
- Quarantine cards must be read-only and may link to the control detail; they must not offer release/re-control until MOB-05C.

### A5. Activité de l’équipe

- Staff name, assigned role/poste, latest verifiable business action and sync state when supported. `qualityControls.staffUid`/`responsable` may provide attributable quality activity.
- No invented presence, performance, ranking or GPS monitoring.

### A6. Détail d’une priorité

- Source record, reason, responsible user only if supported, timeline and one CTA.
- Task assignment only through the existing task contract.

## Flow B — Producer invoices/payables

### B1. Factures producteurs

- Summary: À vérifier, À payer, Payées—only when invoice records exist.
- Filters and invoice cards: producer, linked reception, date, due date, amount and business status.
- Empty state explains that no producer invoice has been received.
- If only estimated payables exist, present a separately labelled `Montants estimés` section.

### B2. Facture à vérifier

- Producer identity and contact.
- Linked reception and source evidence.
- Quantity, agreed price, additional costs and invoice total where real.
- Reconciliation highlights supported differences.
- Actions: `Signaler un problème`, `Valider la facture`.

### B3. Facture validée

- Approved status, amount, due date and timeline.
- `Payer la facture` appears enabled only when backend reports payment capability available.
- Otherwise show `Paiement indisponible pour le moment` and safe retry/refresh.

### B4. Target future payment flow

The UI states are designed now but actual execution is blocked until MOB-06B:

1. Verify producer, amount, reception and idempotent payment reference.
2. Explicit confirmation bottom sheet.
3. Non-dismissible request-in-progress state.
4. Backend-confirmed success, pending confirmation or failure.
5. Receipt/reference shown only from backend response.

No manual `Marquer comme payée`. No locally fabricated success.

## Invoice statuses

Business status and local sync status must remain distinct.

Business statuses: Received, Needs review, Approved, Payment pending, Paid, Disputed, Cancelled. Use repository naming conventions and French UI labels.

Local sync statuses: Pending, Syncing, Synced, Failed.

Status transitions must be validated server-side or by Firestore rules/transaction appropriate to the architecture.

## Required states

- Loading skeleton
- Empty dashboard/module
- Offline with cached data and last-sync time
- Partial cache/data unavailable
- Sync failed with retry
- Permission denied
- Invoice absent
- Invoice/reception mismatch
- Payment capability unavailable
- Future payment pending, successful, failed and unknown-after-timeout

## Navigation and accessibility

- Every authenticated screen and applicable modal retains AppHeader/BackHeader, `Mode Administrateur` and BottomNav.
- Bottom navigation must respect Android/iOS bottom safe areas and never cover CTAs.
- Minimum 48×48 px touch targets, icon plus text, simple French and scalable type.
- Fraunces headings through existing typography tokens; body text uses the existing readable sans-serif.
- Red only for true urgency, dispute or failed payment—not normal unpaid status.

## Acceptance criteria

- ADMIN home uses real cache-first data and provides actionable cross-module visibility.
- No metric, alert, person activity or payable is fabricated.
- All five priority categories are represented when supported by data, including the real MOB-05B quality-control state.
- Productions awaiting control and existing `qualityControls` are reconciled without treating locally queued controls as absent duplicates.
- Quarantined/rejected lots are visible but cannot be resolved in this sprint.
- No finished-goods stock total, availability or stock movement is invented from a quality decision.
- Invoice and estimated payable are never confused.
- Invoice detail reconciles against the linked reception using authoritative calculations.
- No external-provider branding appears anywhere.
- No external secrets exist in mobile code.
- Payment cannot report success without a backend confirmation.
- Role guards and Firestore rules are tested (no organization concept exists to isolate — see Amendment 1).
- AppHeader/BackHeader, role badge and BottomNav are verified screen-by-screen.
- Existing MOB-01 through MOB-05B tests remain green.
- Typecheck, lint, Jest and web export pass.
- Firebase rules tests introduce no regression against the recorded baseline. Run the suite more than once when necessary to distinguish the known first-upload emulator race from deterministic failures; report exact results and never describe a failing run as fully green.
