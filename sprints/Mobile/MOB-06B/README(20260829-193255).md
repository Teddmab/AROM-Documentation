## Objective

Bring every MOB-06A Administrator screen into close visual conformity with the approved AROM references and make the experience understandable to nontechnical users. Add a complete producer-payment simulation using development-only mock data while the real external payment API remains unavailable.

This sprint has two inseparable workstreams:

1. **MOB-06A visual remediation:** redesign every implemented Administrator dashboard and invoice route—not merely restyle individual components.
2. **MOB-06B mock payment flow:** exercise confirmation, processing, success, pending and failure through an injected mock adapter that cannot transfer money or mark a production invoice paid.

## Shared guided-screen design contract

Every MOB-06A and MOB-06B screen must follow this hierarchy:

1. Shared top AppHeader.
2. Persistent `Mode Administrateur` badge.
3. Fraunces page heading, 28–32 px where space permits.
4. One plain-language sentence explaining the screen.
5. Optional connectivity/demo banner.
6. Main content with no more than three or four major cards above the fold.
7. A visible **Que faire maintenant ?** or **Étape suivante** guidance card.
8. One dominant primary action.
9. Shared BottomNav above the system safe area.

Required visual rules:

- Background `#FBF7EB`; primary `#005A2B`; gold/yellow accents.
- White cards, 18–22 px radii, subtle borders/shadows and 16–20 px internal spacing.
- Minimum 48×48 px touch targets and 56 px primary buttons.
- Important text at least 16 px; secondary text at least 14 px.
- Icon or contextual image plus label; never require icon interpretation alone.
- Status uses icon + word + explanation; never color alone.
- One clear CTA per card; avoid rows of equal-priority buttons.
- Generous whitespace; no dense dashboard grids, small tables or unexplained numbers.
- Real images/illustrations help explain receptions, production, quality and people.
- Red only for an immediate problem or failed mock payment.
- Bottom navigation never overlaps content or CTAs.

## Mock architecture and safety

- Use dependency injection behind the existing payment-capability boundary.
- Add `MockProducerPaymentGateway` and fixture repository outside production data access.
- Mock mode requires both development runtime and an explicit local flag.
- Production builds always resolve capability as unavailable regardless of public environment configuration.
- Use deterministic scenarios selectable only in a developer control/test fixture: success, pending, failure and timeout.
- Generate stable mock idempotency references and reject duplicate requests.
- Keep mock state in memory or a namespaced local demo store; never write payment outcome to `producerInvoices` or any real Firestore collection.
- Mock invoices have unmistakable demo metadata and cannot mix with synchronized invoices.
- Do not weaken Firestore rules.
- Remove or tree-shake developer scenario controls from production UI.

## Required states

- Partial data and last-sync time
- Sync failure and retry
- Permission denied
- Demonstration banner

- Duplicate submission prevented
- Production capability unavailable

## Acceptance criteria

- Every Administrator route follows the shared guided-screen contract.
- Users are told what the screen means and what to do next.
- No screen presents a dense web-dashboard layout on mobile.
- Header, role badge and bottom navigation are present and unobstructed throughout.
- The implementation closely matches both reference boards.
- Mock mode is unmistakably labelled on every payment screen.
- Production cannot enable, execute or persist mock payments.
- No mock outcome changes real invoice business status.
- Duplicate mock payment is prevented.
- Existing reconciliation and invoice transition logic remains intact.
- All prior tests, typecheck, lint, rules tests and web export show no deterministic regression.
